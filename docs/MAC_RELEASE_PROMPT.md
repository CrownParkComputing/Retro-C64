Why a Mac at all: the Linux toolchain (`iosbox`) can only produce a debug/JIT
build. iOS kills a Flutter JIT process within a second unless a debugger is
attached, so that build opens and instantly closes from the home screen and
testers cannot run it. Flutter's iOS AOT compiler is macOS-only. The Mac build
is therefore the only one that can be tapped, TestFlighted or shipped.

---

You are building and shipping the first iOS release of **Retro-C64**,
a Commodore 64 emulator. The repo already builds green on Linux, Android and
CI; nothing about the Dart or native code needs changing. Your job is the
macOS-only half: a signed release IPA, and getting it to TestFlight.

## Get it building

```bash
git clone https://github.com/CrownParkComputing/Retro-C64.git
cd Retro-C64/flutter_app
flutter --version          # must be 3.41.9 -- CI pins it, mismatches churn pubspec.lock
flutter pub get
flutter build ipa --release --export-method app-store
```

`brew install cocoapods` first if it is missing. The Linux path never uses
CocoaPods, so this is easy to be caught out by; the macOS build generates a
Podfile and runs `pod install` for `file_picker`, `shared_preferences` and
`http`.

## Three decisions to make before the first upload

1. **The bundle ID is `com.crownpark.retro_c64` (after the Android rename
   that landed with the shared-sidebar refactor) and the app is now
   called Retro-C64.** A bundle ID can NEVER be changed once an App Store
   Connect record exists. Ask the owner whether to rename it (e.g.
   `com.crownparkcomputing.c64-retro`) BEFORE creating the record. If renaming,
   change it in `ios/Runner.xcodeproj/project.pbxproj` and
   `android/app/build.gradle.kts` together, or the two stores diverge.
2. **No `DEVELOPMENT_TEAM` is committed** — deliberately, it is
   account-specific. Set it in Xcode under Signing & Capabilities, or pass
   `--export-options-plist`.
3. **`version:` in `pubspec.yaml` is `1.0.0+1`.** App Store Connect rejects a
   build number it has already seen, and it tells you *after* the upload.

## Do not "fix" these — they are deliberate, and each cost a debugging cycle

- **Do not reintroduce `Main.storyboard` or `LaunchScreen.storyboard` into the
  launch path.** `SceneDelegate.swift` builds the window in code and
  `Info.plist` uses a `UILaunchScreen` dict on purpose: `ibtool`/`actool` are
  macOS-only, so a storyboard build silently ships a bundle with no
  `Main.storyboardc` and every launch dies with `NSInvalidArgumentException`.
  The files remain in the repo and the Xcode project so a Mac build still
  works; nothing reads them at runtime.
- **Do not delete `ios/Frameworks/libvicecore*.dylib` or the Runner target's
  "Embed Frameworks" phase.** Those are the emulator itself, committed because
  building them needs a cross-compiled VICE tree that is not in the repo. They
  are embedded with `CodeSignOnCopy`; an embedded dylib signed by anyone other
  than the app's identity fails App Store validation. Without them the app
  builds, installs, and dies at "Failed to load libvicecore".
- **Do not regenerate the app icons on the Mac.** They are generated by
  `tools/make-app-icons.py` and committed for both platforms. The loose
  `ios/Runner/AppIcon*.png` files exist for the Linux build, which cannot run
  `actool`; on the Mac the asset catalogue wins and the loose ones are inert.
- **`ITSAppUsesNonExemptEncryption` is already `false`** and the three
  `NSUsageDescription` strings are present. The usage strings are required
  because `file_picker` links the camera/photo/location frameworks (validation
  warning 90683), not because the app uses them.

## Verify before uploading

```bash
# the emulator core must be inside the app, or it launches and dies
ls -l build/ios/iphoneos/Runner.app/Frameworks/libvicecore*.dylib
# the icon must be compiled in
ls -l build/ios/iphoneos/Runner.app/Assets.car
```

Then install the release build on a real device and check it **launches from
the home screen icon** — that is the whole point of this build, and the thing
the Linux one cannot do.

## Upload

Transporter, or:

```bash
xcrun altool --upload-app -f build/ios/ipa/*.ipa -t ios \
  --apiKey <KEY_ID> --apiIssuer <ISSUER_ID>
```

The owner also has `simonnilsson/ios-uploader` if you prefer it.

## Known limitations to report, not fix

- **iPhone screenshots do not exist.** `UIDeviceFamily` claims iPhone support,
  so the App Store will ask for them, and they cannot be faked from the iPad
  captures in `store/screenshots/`. Either shoot them on an iPhone or make the
  app iPad-only.
- **The app cannot import `.zip`.** It reads d64/d71/d81/g64/tap/t64/crt/prg/
  p00/sid only.
- On a free developer account a sideloaded build stops launching after 7 days.

## If something breaks
